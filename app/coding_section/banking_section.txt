QUESTION: Original file location: The uploaded file is saved into Supabase Storage (default bucket statement-files) and 
the storage path is recorded in bank_statement_uploads.storage_path. See the upload create handler in bank.py:680-709.

Stored format: The original file is kept as the original binary (PDF/CSV/XLSX/etc.); the DB row stores original_filename, mime_type, file_sha256 and later source_format / raw_extraction after extraction. The code downloads the raw bytes from storage for extraction (db.storage.from_(bucket).download(...)) and computes SHA256. See extraction/download code in bank.py:620-656.
Compression / space: The system does not compress uploads by default. It does deduplicate by file_sha256 (duplicate detection) 
and has atomic delete RPCs that remove storage files. Recommended options: enable dedupe/skip-duplicates (already present), implement retention or tiering (move old uploads to cold storage), or compress/archive large multi-year PDFs if acceptable for your extraction/workflow. No automatic compression is implemented today.
Security around files: Access is protected by JWT + Row-Level Security (RLS) on the DB tables (bank_accounts, bank_statement_uploads have RLS). Server code uses a Supabase service-role client for uploads/extraction; user-scoped clients (RLS enforced) are used for requests. See client handling in supabase_client.py and auth/RLS enforcement in dependencies.py:1-40. Uploads and deletions are logged to bank_audit_events.
Other important notes:
Audit trail: events are recorded in bank_audit_events for upload/extract/post actions.
Deduplication: file_sha256 is used to detect duplicate files before re-processing.
Extraction metadata: post-extract the DB stores extraction_evidence, raw_extraction, confidence_score, and costs (VLM token usage).
Posting flow: a reviewed line → draft journal → post; gl_journals exist and link back to lines, but GL linkage must be set (gl_account_id) for the bank account to appear in TB/transaction reports.
Deletion/cleanup: uploads are removable via atomic RPCs that also delete storage files (see delete handlers).

USER QUESTION: When a bank statement is imported, where is the information saved? Is there a view where I can see/edit/delete draft journal entries after review? At the moment when it says it has posted, I cannot find it on the Transaction Listing report or the TB Report. Is there a "hard core" no to unbalanced Dr's and Cr's for a transaction?

CODEX ANSWER: 

There are real gaps here.

1) Original file: Supabase Storage, usually statement-files. 
2) Upload metadata: bank_statement_uploads.
3) Extracted transactions: bank_statement_lines.
4) Draft/posted journal headers: gl_journals.
5) Debit and credit entries: gl_journal_lines.
6) History: bank_audit_events.

Reviewing does not automatically mean GL posting. A normal bank line progresses through:

1) reviewed → draft journal created → journal posted
2) The Transaction Listing only reads gl_journals.status = 'posted' within its selected date range. 
   The TB similarly reads posted journals up to the selected date. Therefore, if an entry is genuinely 
   posted with the correct organisation and journal date, it should appear in both reports. See 
   [transaction_report.py (line 66)](C:/Users/dale/Documents/apflow-backend/app/services/transaction_report.py:66) 
   and [trial_balance.py (line 106)](C:/Users/dale/Documents/apflow-backend/app/services/trial_balance.py:106).
3) The likely causes are:
3.1) The line was reviewed but no GL journal was posted.
3.2) The report date range excludes the bank transaction date.
3.3) The UI says “posted” based on the bank-line status while the linked journal is missing or inconsistent.
3.4) The journal lines reference missing/unavailable accounts.
3.5) A frontend workflow is skipping the draft/post endpoints.

There is currently no proper journal-register view/API for listing, editing and deleting all draft journals. The backend can:

1) Preview a journal.
2) Create a draft.
3) Retrieve that journal’s lines.
4) Post it.
5) Reverse it after posting.

It cannot directly edit or delete a draft journal. Deleting its underlying bank line/upload indirectly removes associated drafts. Also, requesting a draft again simply returns the existing one instead of updating it. See [bank.py (line 1152)](C:/Users/dale/Documents/apflow-backend/app/routers/bank.py:1152).
On balancing: the ordinary builder produces balanced two- or three-line journals, and gl_journals has a constraint requiring its stored total_debit and total_credit to match. However, there is no database-level check that those header totals equal the actual sum of gl_journal_lines. The posting endpoint also does not recompute and verify the line totals before setting status = 'posted'.
So the honest answer is: no, there is not yet a “hard-core” database guarantee preventing an unbalanced collection of journal lines from being posted. Normal application use constructs balanced entries, but the accounting invariant is not fully enforced. The missing safeguard should be an atomic database posting function that sums the lines, requires at least two valid lines, confirms debit equals credit, and only then marks the journal posted.

2. Extraction

POST /api/bank/uploads/{id}/extract triggers the pipeline in app/services/bank_statement_extraction/pipeline.py:

CSV/XLSX → dedicated column-inference parsers
PDF (text) → regex date/amount anchor parser
PDF (scanned/complex) → Gemini VLM fallback with parsing hints
Outputs: bank_statement_lines rows + balance validation + duplicate detection

2.1 Multi-month, one .PDF, Upload

The PDF should be treated as a container of statements:

1) Read every page independently using selectable text or OCR.
2) Identify account number, statement period, page number, opening balance and closing balance.
3) Group pages belonging to the same monthly statement.
4) Order groups chronologically by statement dates—not by balance values alone, because balances can rise or fall.
5) Send each monthly group through extraction separately.
6) Validate each month:
    opening balance + transaction movement = closing balance
7) Validate continuity:
    January closing balance = February opening balance
8) Detect gaps, overlaps, missing pages and inconsistent account numbers.
9) Deduplicate using a transaction fingerprint containing date, amount, reference, description and account—not transaction count alone.
10) Stage questionable months for review while accepting clean months.

The original five-year PDF should remain one parent upload, with approximately 60 child “statement segments.” Each child behaves like an independently uploaded monthly statement and retains page-level provenance.
This also solves the current 10-page AI fallback limit because the AI receives only one monthly segment at a time. The existing transaction fingerprinting in [common.py](C:/Users/dale/Documents/apflow-backend/app/services/bank_statement_extraction/common.py) and duplicate pipeline can be extended for this workflow.
The critical principle is: use dates, account identity, page numbering and balance continuity together. Opening and closing balances alone are not reliable enough to determine page order.

The harder parts are:

1) Correctly grouping multi-page monthly statements.
2) Handling dates without years across five years.
3) Detecting missing, repeated, or out-of-order pages.
4) Distinguishing genuine duplicate transactions from identical legitimate payments.
5) Validating monthly balances and continuity.
6) Supporting scanned PDFs and low-confidence OCR.
7) Preventing partial imports when one month fails.

2.2 Cleaning up the extraction

a) "Balance brought forward", "Opening balance", "Closing balance", "Balance carried forward" should be imported
for accuracy and not for reconciliation.
b) Some bank charges will only show a line of information, but no amount. These need to be excluded from
the reconciliation page.

4. Post

POST /api/bank/lines/{id}/draft-journal → POST /api/bank/journals/{id}/post:
Creates a double-entry gl_journals record (source_type = 'bank_transaction')
Two or three gl_journal_lines: bank GL account + allocation GL account (+ optional VAT split)
Can be reversed with /unpost which creates a reversal journal and resets the line

Key Tables
Table	What it holds
bank_accounts	Account metadata, GL link, opening balance
bank_statement_uploads	File metadata, extraction status, balance evidence, confidence
bank_statement_lines	Extracted transactions — all status flags (match/allocation/posting/review)
bank_transaction_rules	User-defined auto-allocation rules (pattern → GL account)
bank_transaction_suggestions	AI/rule suggestions per line (invoice match, rule match)
bank_audit_events	Full event trail (upload → extract → review → post → unpost)
bank_parsing_rules	VLM extraction hints per bank/account type
Backend Endpoint Groups (/api/bank/...)
Accounts: list, create, unreconciled lines + balance summary
Uploads: list, register, extract, delete, get lines, audit trail
Lines: delete, suggest, review, journal preview, draft journal
Journals: post, unpost, get lines
Parsing rules: CRUD for VLM extraction hints

Key Design Choices

Extraction is format-agnostic — the parser is selected by registry (format + account type), 
 CSV and XLSX parse deterministically, PDF falls back to VLM only if text extraction yields no lines.
Posting is reversible — unposting creates a counterpart reversal journal rather than deleting, 
 preserving the audit trail.
Rules are learnable — after reviewing a transaction, the user can save the allocation as a rule 
 so future matching transactions are suggested automatically.
